# RinaBoard 多板（两块及以上）压力测试计划

编写于 2026-09-13。依据是当前工作区（HEAD `1e81ff0` 加未提交修改，含「换板放弃未保存画面」修复）的源码，以及 `docs/stress-ui-20260913-012607/` 首轮双板真机结果。

本计划只覆盖**两块及以上的板同时存在**时才会出现的问题。板数不固定，以脚本每次扫描实际搜到的板为准；下文用 A、B 举例，C、D… 同理。覆盖范围：
- 命令路由
- 会话身份
- 状态隔离
- 输出所有权
- 连接生命周期

单板功能的逐页覆盖仍按 `STRESS_TEST_UI_PLAN_ZH.md` 执行。执行前重新核对源码，与本文不一致时以源码为准，并在报告中写明差异。

## 0. 目标

1. **命令零串板**：两块板都在线时，界面上的每一次操作，只作用于当时的控制对象（active 板）。
2. **身份一致**：「控制对象」「已保存的璃奈板」、控制中心「面板」菜单、状态页，四处显示的板与实际连接的物理板一致；不会出现同一块板对应两个会话，或一个会话挂着两块板的身份。
3. **状态不串**：颜色、亮度、模式、间隔、表情序号、表情库、文字进度、预览、电量、编辑器草稿，都跟随当前控制对象；非控制对象的板不被改动。
4. **并存稳定**：两块板各自播放（固件自走的文字或自动表情，加手机推流）、各自掉线重连时，另一块不受影响，App 不崩溃、不卡死。
5. **大量切换后收敛**：用固定种子长时间随机切换，结束后所有板的状态与 App 显示一致，资源回落。

### 0.1 脚本规则（用户决定，2026-09-13）

- **R1 连接全部**：以下时机，脚本打开 连接 → 扫描附近的璃奈板，等扫描结束（30 s 自动停止），然后对扫描列表里**每一块**搜到的板逐个点「連線」（已在线的跳过），直到「控制对象 · N 块在线」等于搜到的板数：
  - 测试开始时
  - 每次 App 重启后
  - 每次有板恢复供电后

  板数不固定，不预设只有两块。App 启动时仍只自动连一块，其余由脚本手动连接。
- **R2 掉电不自动切换**：当前控制的板掉电或断开时，App 保持现状、不自动换板，这是预期行为。
- **R3 由脚本切换**：检测到当前控制的板离线后，脚本在 5 s 内打开「控制对象」列表，检查是否还有其他在线的板：
  - 有：点击列表中第一块在线的板，切换后继续测试。
  - 没有：等待，并按 R1 重新扫描连接。

  每次切换都记入步骤 CSV：离线的板、发现时刻、切到的板、耗时。
- **R4 板集合动态**：随机游走、路由判定、状态快照都针对当前在线的全部板，不硬编码 A/B。

## 2. 读码确认的双板模型（执行前复核）

- **会话**：`BoardSessionStore` 为每块板维护一个 `BoardSession`，各自持有 `BoardConnection` 和 `BLETransport`。同一时刻只有一个 `active`，界面和各功能的单例模型都连到 `sessions.active.connection`（`RinaBoardApp.swift:27-42`）。
- **功能模型都是 App 级单例**：编辑器、文字、控制中心、表情库、口型、演出、视频（`RinaBoardApp.swift:12-18`）。换板时由 `RootTabView` 的 `BoardSynchronizationID` 任务统一处理：
  - 表情库：同步代次。
  - 控制中心：取消待发值，清空回显抑制窗口。
  - 文字：挂起预览。
  - 编辑器：连接变化时释放输出，**换板时放弃草稿**。
  - 口型：停止。
  - 演出、视频：停止向板子推流，手机本地播放和声音继续。
  - 已连接时重新读取板子状态，并切到板子当前模式对应的页面。
- **切换入口**：

  | 编号 | 入口 | 行为 |
  | --- | --- | --- |
  | E1 | 连接页「控制对象」行 | `sessions.select`，只换 active；旧板保持连接，旧会话的输出租约失效 |
  | E2 | 控制中心「面板」菜单 | **复用当前 active 连接**：先断开当前板，再连目标板（`BoardControlCenterView.swift:167-175`） |
  | E3 | 已保存面板行、扫描列表行 | `selectSession(id:)` 找到或新建会话后连接（`ConnectionView.swift:197-206`） |
  | E4 | 启动时自动重连 | 选 `lastSeen` 最新的板；草稿恢复期间用户手动选择优先 |
  | E5 | 忘记面板 | `sessions.remove(id:)` 断开并移除匹配的会话，同时从已保存列表删除 |

- **板身份**：`BoardConnection.boardIdentity`，握手时从 `wifi.boardId` 或 `get_info.defaultName` 取 MAC 编号。`boardKey` 为 `board:<id>`，取不到时退回 `ble:<UUID>` 或 `wifi:<host>`。会话匹配 `BoardSession.matches` 用的是 `boardID` 加别名集合（BLE UUID、Wi-Fi host），**不用** `boardIdentity`。
- **已知缺陷**（首轮复现，本计划作回归项）：
  - **DB-BUG-1（高，MB-10；修复方向已定：目标板已在其他会话在线时，E2 直接选中那个会话）**：用 E2 切到一块已在另一会话连着的板，会在同一条 BLE 链路上建立第二个会话（该板 slot 0 上出现第二次 `subscribe`/`get_info`）。原板被断开，「控制对象」显示 2 块在线但两行都是同一块板。
  - **DB-BUG-2（中）**：E2 热切换后，会话的 `boardID` 仍是旧板，别名里又加入了新板。点已保存的旧板无任何反应、不报错。按代码推断还有两个后果，尚未验证：扫描列表连旧板会再次热切换同一会话；「忘记」旧板会断开当前的新板。
  - **遗留风险**：握手时两次读取板身份都失败，同一块板可能被当成另一块，草稿被放弃。
- **固件**：
  - 每块板的 BLE 名、mDNS 主机名、AP SSID 都带 MAC 后缀。
  - 每块板最多 2 个 TCP 客户端。
  - 所有板的 SoftAP 同一个 IP，手机同一时间只能加入一个热点。
  - `status` 输出 `lit=`、`accepted=`（已接受帧计数）、`lastReason=`、`faceIndex`、`mode`、`brightness`、`color`、`intervalMs`，是判断「哪块板收到了什么」的主要依据。
  - debug 日志记录 `[PROTO] event=command name=<cmd>`，但**不记录 SET_FRAME 内容**。首轮点 › 时没抓到 `button` 行，执行前确认各类命令的日志格式。

## 3. 判定方法

### 3.1 硬性不变量（任一违反即 FAIL）

| 编号 | 不变量 |
| --- | --- |
| INV-1 零串板 | 非 active 板的串口日志里，不出现本步骤发起的 CMD；它的 `accepted`、`faceIndex`、`mode`、`brightness`、`color`、`intervalMs` 均不变 |
| INV-2 会话唯一 | 任一时刻，一块物理板最多对应 1 个 App 会话；一个会话只对应 1 块物理板。检查方法：「控制对象」行数与去重后的板身份一致，每块板串口中来自手机的 `subscribe` 与会话数一致 |
| INV-3 身份一致 | 状态页「已连接璃奈板」、控制对象的勾选行、控制中心「面板」菜单的勾选项、电量读数，与 active 板的串口身份一致 |
| INV-4 收敛 | 负载停止 3 s 后，App 显示的颜色、亮度、模式、间隔、表情序号，与 active 板 `status` 一致；预览与该板 `GET_FRAME` 一致 |
| INV-5 旧输出停止 | E1 或 E2 切走后，旧板不再收到任何手机推流帧（`accepted` 不再增长），除非用户在切回后主动继续 |
| INV-6 草稿 | 换到另一块板时编辑器草稿被放弃；同板重连保留；发给新板的帧不含旧草稿 |
| INV-7 无崩溃、无悬挂 | 非强退用例中 App PID 不变；无「连接中」无限转圈；不会有两块板同时显示为 active |
| INV-8 恢复 | 强退或板重启后，从 App 可用（或板上线）起 60 s 内，脚本完成 R1、R3 后：所有可达的板都在线；会话唯一（INV-2）；INV-3、INV-4 成立；板端没有测试注入之外的重启或 watchdog；手机上没有 RinaBoard 崩溃报告 |

### 3.2 证据链

- **步骤日志**：每一步写一行 CSV，包含主机时间戳、种子、步骤编号、入口、操作、当时的 active 板（从 App UI 读取）、预期受影响的板。
- **板端采样**：每步前后各给两块板发一次 `status`（间隔 ≥ 1.5 s），记录 `accepted/lit/lastReason/faceIndex/mode/brightness/color/intervalMs`，以及该时间窗内的 `event=command`、`event=connect/disconnect`、`subscribe`。
- **判定脚本 `oracle.py`**：合并两块板日志和步骤 CSV，逐步检查 INV-1/2/5，输出 `ROUTING.csv`（步骤、预期板、A 的变化、B 的变化、判定）。
- **UI 证据**：失败步骤保存截图，以及「控制对象」列表和控制中心「面板」菜单的截图。

## 4. 用例

每个用例都要记录前置状态（A、B 的在线情况和 active 板）、入口、次数、种子、证据路径。

### 4.1 DB-ID 身份与列表

| ID | 场景 | 步骤 / 规模 | 通过条件 |
| --- | --- | --- | --- |
| DB-ID-01 | 冷启动后连接全部（R1） | 杀 App 重启 → App 自动重连一块 → 脚本扫描，逐个连接其余所有板 | 控制对象行数 = 搜到的板数，每行身份各不相同；已保存行数一致；INV-3 |
| DB-ID-02 | 两块板同名 | 把 A、B 改成同一个名字，再执行 DB-ID-01 和 DB-SW-01 | 列表仍能区分（显示 MAC 后缀或其他标识）；每次都连到正确的板；结束后恢复原名 |
| DB-ID-03 | 改名跟随 | 在 A 上改名，切到 B 再切回 A，杀 App 重启 | 名称只改 A；各处显示一致；B 不受影响 |
| DB-ID-04 | 忘记 active 板 | A active、B 在线时忘记 A | A 断开并从列表消失；B 保持连接并成为 active（或提示需要选择）；B 的状态不变 |
| DB-ID-05 | 忘记非 active 板 | A active 时忘记 B | 只有 B 断开；A 不受影响 |
| DB-ID-06 | **回归 DB-BUG-2** | 做一次 E2 热切换 A→B 后：① 点已保存的 A；② 从扫描列表连 A；③ 忘记 A | 修复前记录实际行为（①无响应、②③预期出错）；修复后：①② 在独立会话中连上 A，B 保持连接；③ 只影响 A |

### 4.2 DB-SW 切换入口矩阵

目标板有三种状态：离线、已在另一会话在线、刚断开。每格至少 20 次，E2 与 E1 各做一遍。

| ID | 入口 × 目标状态 | 通过条件 |
| --- | --- | --- |
| DB-SW-01 | E1 × 另一会话在线 | 只换 active；两块板都不断开；INV-3、INV-5 |
| DB-SW-02 | E1 × 离线会话 | 选中后显示未连接，控件禁用；该板重新上线后状态正确。另外记录：离线期间在编辑器画的草稿，上线后会被放弃（草稿属于原板） |
| DB-SW-03 | E2 × 离线板 | 当前板断开，目标板连上；只有 1 个会话对应目标板；原板在已保存列表中仍可再连（DB-BUG-2 回归） |
| DB-SW-04 | **E2 × 另一会话在线（回归 DB-BUG-1）** | 预期（修复后，用户选定方案 1，2026-09-13）：直接切到目标板已有的会话（等同 E1 选中）。当前板保持连接，不发起新的 BLE 连接或握手：目标板串口里没有新的 `subscribe`/`get_info`，当前板没有 disconnect；「控制对象」勾选移到目标板，在线数不变；不产生第二个会话；原板不被断开；INV-2 |
| DB-SW-05 | E3 已保存行 × 在线/离线 | 在线时相当于选中；离线时新建或复用正确的会话并连接 |
| DB-SW-06 | E3 扫描行 × 已在另一会话在线的板 | 不重复连接；列表中不出现两份同一块板 |
| DB-SW-07 | E4 启动选板 | A、B 交替作为最后使用的板，重启 ×10；启动后立即手动选另一块；最后使用的板断电时重启 | 按 `lastSeen` 连接；手动选择优先；目标断电时有明确提示，不卡在启动动画；随后脚本按 R1 连上其余板 |
| DB-SW-08 | 切换进行中再操作 | E2 连接中时：点另一块板、点同一块板、点断开、切标签页、拉起控制中心；E3 连接中时点另一行 | 最终只连到最后一个有效目标；按钮禁用状态正确；INV-2、INV-7 |

### 4.3 DB-RT 命令路由（两块板都在线）

每个操作：用 E1 让每块在线的板依次成为 active，各做 N 次，最后回到第一块再做 N 次。每组做完后，判定脚本对所有非 active 的板检查 INV-1。

| ID | 类别 | 操作 | 次数 N | 板端判据 |
| --- | --- | --- | --- | --- |
| DB-RT-01 | 全局设置 | 颜色预设、亮度滑块、间隔滑块 | 各 10 | 只有 active 板的 `color/brightness/intervalMs` 变化 |
| DB-RT-02 | 模式与表情 | A/M、‹、› | 各 5（计入 flash 预算） | active 板 `mode/faceIndex` 变化，另一块不变 |
| DB-RT-03 | 编辑器帧 | 实时预览下点灯、随机、清空、传送 | 各 10 | active 板 `accepted` 增长且 `lastReason` 为 `custom_*`；另一块 `accepted` 不变 |
| DB-RT-04 | 表情库 | 打开列表、应用表情（只读） | 各 5 | 应用只改 active 板的 `faceIndex/lit`；表情库内容为该板自己的库（先让两块板的库有可辨识差异，或比较条目数） |
| DB-RT-05 | 文字 | 发送并播放、暂停、单步、seek、改 fps、停止 | 各 3 | `[SCROLL]` 日志只出现在 active 板 |
| DB-RT-06 | 口型 / 演出 / 视频 | 开始 10 s 后停止 | 各 2 | 推流帧（`accepted` 增长，`lastReason` 为 `lipsync:`、`live_preset:` 或 `video:`）只出现在 active 板 |
| DB-RT-07 | 调试 | PING、刷新全部、测试图案发送、按键模拟 B1 | 各 5 | 只出现在 active 板；调试页显示的是 active 板的数据 |
| DB-RT-08 | 连接页 | 刷新名称、扫描 Wi-Fi（只读） | 各 3 | `get_info/wifi_scan` 只出现在 active 板 |

### 4.4 DB-INF 切换瞬间的在途操作

分别在切换前 0、50、150、300 ms 执行下列操作，E1、E2 各做一遍，每格 10 次（共 7 × 4 × 2 × 10 = 560 次，建议自动化）：
1. 连续拖动亮度或颜色（LatestValueSender 合并中）
2. 拖动间隔滑块
3. 实时预览快速涂画（帧队列深度 6）
4. 连点 ‹ › 或 A/M（命令队列深度 4，计入 flash 预算，每组最多 5 次）
5. 表情库应用、重命名进行中（重命名计入预算）
6. 文字上传进度约 50 %
7. 调试页连续发送测试图案

**通过条件**：
- 切换后，新 active 板收不到任何切换前发起的命令或帧（INV-1）。
- 旧板上的 BLOB 事务被中止或超时回收，不留下 `active=1, frameCount=0`。
- 表情库写操作被 `validateBoard` 拦截，并提示「面板已更换」。
- E2 路径另外检查：帧队列、命令队列中已排队、尚未开始的任务，是否在新板连上后才被执行（首轮读码时的疑点，至今未证实）。

### 4.5 DB-OUT 双板输出并存

| ID | 场景 | 步骤 | 通过条件 |
| --- | --- | --- | --- |
| DB-OUT-01 | 两块板各自滚文字 | A 滚文本 1，B 滚文本 2；E1 来回切 50 次，停留 0.3–5 s | 两块板的固件滚动不受切换影响（用 `log level trace` 的 tick 测 fps，偏差 < 2 %）；App 显示的文本、进度、fps、循环始终跟随 active 板；在 B 上暂停或 seek，不影响 A |

### 4.8 DB-FQ 强制退出 App

**强退方式**：每个用例都要覆盖 Q1、Q2，Q3 抽样。

| 方式 | 做法 |
| --- | --- |
| Q1 | 主机 `devicectl device process terminate --pid <pid> --kill`（SIGKILL，App 来不及保存草稿） |
| Q2 | XCUITest `XCUIApplication().terminate()` |
| Q3 | 人工通过 Device Hub 在 App 切换器上划掉（系统先让 App 进后台再终止），每用例至少 3 次 |

强退后的恢复流程：重新启动 → App 按 E4 自动连一块 → 脚本 R1 连上其余全部板 → R3 确保 active 板在线 → 检查 INV-8。

| ID | 强退时机 | 步骤 / 规模 | 通过条件 |
| --- | --- | --- | --- |
| DB-FQ-01 | 空闲 | 全部板在线、无播放；×20 | 每块板串口出现一次 BLE disconnect；重启后 INV-8；已保存列表完整；没有重复会话 |
| DB-FQ-02 | 播放中 | active 板运行 7 个输出来源之一，另一块板运行另一个来源；每个来源 ×5 | 文字、自动表情由固件继续自走；推流类（实时编辑、口型、演出、视频、调试）板端 `accepted` 停止增长，画面停在最后一帧；重启后 App 只按 active 板的状态恢复页面；其他板不被 App 改动 |
| DB-FQ-03 | 切换进行中 | E1 点击后 0、100、500 ms；E2 连接中；R1 正在连第 k 块；R3 切换中；各 ×10 | 重启后没有重复会话、没有连错板；板端 `client_connect` 与 `disconnect` 成对，没有残留的半截握手 |
| DB-FQ-04 | 事务进行中 | 文字上传约 50 %、表情库导入（BLOB）、表情重命名或排序、设备名保存；各 ×3–5，写操作计入 flash 预算 | 板端 BLOB 在 30 s 内回收，不留下 `active=1, frameCount=0`；表情库哈希等于操作前或操作后之一，没有半写；名称为旧名或新名之一 |

| DB-FQ-07 | 连续强退 | 启动后在 0.5、2、5 s 随机强退，循环 100 次 | 手机上没有 RinaBoard 崩溃报告；板端每次都有 disconnect，连接槽没有耗尽；最后一次正常启动后，全部板都能连上 |

### 4.9 DB-RB 板子重启

目标板必须先用串口 `boardId` 确认身份。重启由用户要求纳入本计划（2026-09-13），只对确认身份的测试板执行。

**重启方式**：

| 方式 | 做法 |
| --- | --- |
| B1 App 指令 | 设定 → 重启面板，或调试 → 重启设备；发 `reboot` 命令，只作用于当前 active 板 |
| B2 硬件复位 | 主机通过 USB 串口的 RTS/DTR 触发复位，或人工按板上的 RESET 键。先在单板上验证 B2 可靠、不会进入下载模式，验证通过后才用于批量 |
| B3 断电重启 | 断开 USB 供电和电池开关（人工操作，或使用可编程电源） |

**证据**：串口日志 uptime 归零并出现 `startup_sequence_complete`；BLE disconnect，随后 connect；App 会话状态变化。

| ID | 场景 | 步骤 / 规模 | 通过条件 |
| --- | --- | --- | --- |
| DB-RB-01 | 空闲时重启 active 板 | B1、B2、B3 各 ×5 | App 显示离线，不自动换板（R2）；脚本按 R3 切到其他在线板；目标板启动后在退避时间内自动重连，但不抢回 active；重连后颜色、亮度、模式、间隔、表情序号从 flash 恢复，且与 App 显示一致 |
| DB-RB-02 | 重启非 active 板 | 以 B2、B3 为主，×10；B1 需要先切过去发指令再切回，×3 | active 板的操作不中断、不串板；非 active 会话自动重连；「控制对象」在线数先减后恢复 |
| DB-RB-03 | 播放中重启 | active 板在文字、自动表情、视频、演出、口型、实时编辑中的一种状态下，用 B2 重启；另一块板播放另一个来源；每种 ×3 | App 对应功能进入停止或等待状态，不崩溃，也不转而向其他板推流；板重新上线后，App 按板状态恢复；另一块板的播放不受影响 |
| DB-RB-04 | 事务中重启 | 文字上传中、表情库导入中、设备名保存中（计入预算）；各 ×3。Wi-Fi 配置保存中需另行征得同意，可选 | App 请求失败时有提示，并释放锁和进度状态；板启动后旧数据完整（表情库哈希、名称为旧或新之一）；再次操作成功 |
| DB-RB-05 | 握手或切换中重启 | E2、E3 连接中；R1 连接全部进行中；握手的 `get_info` 前后；各 ×5 | 不会连错到另一块板；不出现重复会话；R1 最终连全 |
| DB-RB-06 | 全部板一起重启 | B1 依次重启；B2 同时重启；各 ×10 | 所有会话进入重连；按上线顺序执行 R3、R1；不串板；App 不卡死 |
| DB-RB-07 | 反复重启 | 同一块板每 20–60 s 随机重启，持续 20 min，同时在其他板上跑 DB-S-03 | 其他板零串板；该板每次都能重连，记录重连耗时 p50、p95；App 内存不持续增长 |
| DB-RB-08 | 重启后的草稿与状态 | A 上有草稿 → 重启 A → 自动重连；×5 | 同一块板重连保留草稿（INV-6）；若重连后读板身份失败导致草稿被放弃，记为遗留风险 |
| DB-RB-09 | 重启与强退交错 | 板重启过程中强退 App；App 启动过程中重启板；各 ×10 | 同 DB-FQ-06 |

## 5. 自动化方案

1. **XCUITest 真机**：在 `ios/RinaBoardUITests` 新增 `DualBoardStressUITests`。
   - 为控制对象行（带板身份后缀）、控制中心「面板」菜单项、已保存行、扫描行、忘记按钮、各发令控件补 `accessibilityIdentifier`，只加标识，不改行为。
   - 每一步把 `{ts, seed, step, entry, action, activeBoardIdFromUI}` 写到测试附件或 App Group 文件，结束后导出。
   - 通过 launch argument 注入种子与步数。
   - 公共步骤 `connectAllDiscovered()`（R1）：
     1. 进入连接页，点扫描，等扫描结束。
     2. 读取扫描列表的全部行。
     3. 对每个未在线的行点「連線」，等「控制对象」在线数 +1。单块超时 20 s，重试 1 次仍失败则记为 BLOCKED。
     4. 断言在线数 = 扫描到的板数。
   - 公共步骤 `forceQuitAndRecover(method)`：
     1. 按 Q1、Q2 或 Q3 强退。Q1 由主机执行，通过共享标记文件与 XCUITest 同步。
     2. 重新启动 App，等启动动画结束。
     3. 依次执行 `connectAllDiscovered()` 和 `ensureActiveOnline()`。
     4. 检查 INV-8，把各阶段耗时写入 `RECOVERY.csv`。
   - 公共步骤 `rebootBoard(boardId, method)` 和 `waitBoardBack(boardId)`：
     - 按 B1、B2 或 B3 重启。执行 B1 前确认该板就是 active 板。
     - 以串口 uptime 归零加 BLE connect 作为「板已恢复」的判据，超时 90 s。
   - 公共步骤 `ensureActiveOnline()`（R3）：每步开始前读取当前控制对象的在线状态。离线时打开「控制对象」列表，点击第一块在线的板；没有在线板时调用 `connectAllDiscovered()` 并等待。
2. **主机端 harness**（`docs/stress-dual-<ts>/tools/`）：
   - `serial_logger.py`：带时间戳，含停更自动重开。
   - `sample_status.py`：按步骤 CSV 在每步前后给两块板发 `status`。
   - `oracle.py`：合并日志并判定 INV-1/2/5，输出 `ROUTING.csv`。
   - `relaunch_loop.py`：devicectl 按 pid 结束再启动，不用 `--terminate-existing`。
3. **断电与超出范围**：使用可编程 USB 电源开关（如有）；没有时由人工在指定步骤操作，并在步骤 CSV 标记人工。
4. **Device Hub 电脑操控**只用于：首次配对和权限弹窗、断电和移动类人工步骤的截图取证、失败现场复核。

4. `SESSIONS.csv`：每次切换后的会话快照（控制对象行、每块板的 `subscribe` 计数、active 板）。
4a. `RECOVERY.csv`：每次强退或重启一行，包含注入时刻、方式（Q1–Q3、B1–B3）、当时各板的状态与播放来源、各板重连耗时、R1 和 R3 耗时、INV-8 结果、崩溃报告有无。
5. `logs/`：两块板串口原始日志、合并时间线、步骤 CSV、XCUITest 结果包、崩溃报告。
6. `metrics/`：两块板的 heap、`refreshMaxUs`、滚动 fps、App 内存曲线。
7. `RUNBOOK.md`：构建与安装、harness 命令、种子、设备身份、恢复步骤（颜色、亮度、模式、间隔、名称、表情库哈希）。
