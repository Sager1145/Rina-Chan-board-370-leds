# 表情保存在板子、App 按连接读取：保存设计与验收范围

日期：2026-10-15。本页保留设计阶段的方案与发现；后续实施、软件验证和两板验收结果见 [实现报告](2026-10-15-board-owned-faces-implementation.zh-CN.md)。

## 已确认的需求

1. 已保存表情的唯一正式存储在板子上；App 从当前板子读取。
2. 未连接板子时不显示保存列表。
3. 保存到板子的表情可由实体按钮切换，也参与固件自动切换；不依赖 App 持续连接，重启后保留。
4. 可以把表情部件写入固件。纯部件构造的表情可以仅保存部件编号。
5. 自定义表情也要有明确、可靠的保存方法。
6. 测试按钮业务动作可以从串口触发 GPIO 按钮使用的同一路径。
7. 用户确认允许恢复未保存草稿，但草稿不进入保存列表。

## 当前实现与本轮发现

当前同时存在板上 saved_faces.json、本机 local_faces.json、持久化编辑草稿 Drafts/face.json。板上文档读回放在 FaceLibraryModel 的内存状态中，切换和更新有物理身份与连接代次保护。当前离线仍能打开本机列表，已实测，与新要求不符。

当前部件表情仍保存 frameBytes 和 call，尚不支持只存编号。固件 RuntimeFace 载入所有可用保存表情，按钮与自动播放都读取这一份运行列表。

本轮两个独立探针确认了保存边界缺口：

- 他端重命名后，经 reload 得知的新名字可能被误当成“本会话重命名”，旧编辑稿因此更新 expect 基线并覆盖他端名字。
- 新增写入 ACK 已成功，但随后的 GET_FACES 失败时，保存会返回成功且缺少创建的 ID；再次保存又发送无 ID 的新增，可能重复创建。

原有保存与控制/同步测试仍通过；新增探针刻意要求安全边界，失败证明的是原有未覆盖行为，不是本轮产品回归。探针源码已归档到 /tmp/rina-save-review，未保留在产品测试目录。

## 推荐的用户流程

连接到板子并完成物理身份校验后，App 读取这块板子的完整保存列表。界面只称“板上表情”，不再让用户选择“本机／当前板子”。读取期间显示加载；读取失败显示读取失败，不把失败显示成空列表，也不显示另一块板的旧数据。

点击保存时，目标固定为当前已验证的物理板 ID。命名期间断线、切换板子或编辑内容发生变化，不能静默改存另一块板。未连接时隐藏保存列表入口；已打开的列表在断线时关闭。保存不可用，不排队等待未来某块板自动接收。

用户已确认允许跨 App 退出恢复未保存草稿。保留 DraftStorage，但内容明确标记为未提交草稿，带来源板 ID、编辑目标和原始冲突基线；它不进入保存列表、不自动写到重连后的板子，也不绕过切板身份保护。local_faces.json 不再接受新的正式表情保存。连接信息和界面偏好不属于表情库。

## 两种保存内容

继续沿用 id、name、order、type、默认表情保护和启动表情属性，增加部件目录标识与版本。

### 纯部件表情

固件内嵌稳定部件目录，由 App 现有 expression_parts.json 同源生成。当前目录为 rina_expression_parts_370_runtime_v4，版本 4，包含 92 个存储部件，其原始逻辑位图为 92×47＝4,324 字节，不含查找表及版本元数据。

保存四个调用编号和目录版本，不保存合成后的 frameBytes。例如：

```json
{
  "id": "user_3e33b241-90ad-4a8c-8e91-6d39ff5e34f8",
  "name": "笑脸",
  "type": "parts",
  "partsCatalog": "rina_expression_parts_370_runtime_v4",
  "partsVersion": 4,
  "call": {"leye":"101","reye":"201","mouth":"301","cheek":"400"},
  "order": 12
}
```

复用现有编号，包括各组的空部件和 cheek 的 400→0 别名，不按数组位置重新编号。固件将四个已定位、已镜像的逻辑位图按位 OR；蛇形布线映射仍只由渲染器处理，不能在保存与渲染两处重复映射。

只有画面完全由所选部件组成时使用这个格式。基于部件再画一个像素、擦除、反相等，都应改存自定义位图。当前编辑器已有 fromParts 状态，实施时仍需以实际合成结果与画布相等作为最终校验，防止过期元数据导致丢失手绘内容。

### 自定义表情

当前产品的每颗 LED 在表情中只有亮／灭状态，因此保存最终 370 位掩码即可。有效载荷固定 47 字节，最后一个字节只允许低两位有效。颜色和亮度继续使用板级设置。

为减少迁移风险，初版继续使用现有 JSON frameBytes 数组承载这 47 字节，保留 name/id/order 等字段。47 字节是像素数据大小，不是完整 JSON 文件或单条记录的大小。无需 PNG、矢量路径、逐帧历史或压缩格式。

现有传输仍可使用 frameHex 的 94 个十六进制字符；固件落盘转换为 frameBytes。以 type 区分两种内容，互相切换时删除旧表示中不再适用的字段。

## 固件中的统一运行列表

在现有 RuntimeFace 安装路径扩展共享的 materializeSavedFace 逻辑，供保存前校验、启动载入、保存后安装和当前帧应用复用，不另建第二套运行表：

- parts：校验目录版本、组别和全部编号，再合成 47 字节。
- custom/default：读取并校验现有 47 字节位图。
- 将结果放入 RuntimeFace.frameBits，保留该项 id、name、order 和保护属性。

因此按钮 B1/B2 与 serviceAutoPlayback 继续使用同一 RuntimeFace 列表，不需要各实现一遍部件渲染。新保存项在写入与安装成功后即可参与切换。保存仅改变表情库，不隐式改变当前显示，除非用户明确点击应用。

保存前拒绝未知编号、错误组别、错误目录版本或非法位图，保留旧文件。启动遇到不可解析项时保留原始文件和错误信息，继续载入其余有效项，不把损坏内容自动改写成空表情。启动目标失效时，选择首个有效默认表情，再退到首个有效表情；全部不可用时保持清屏并报告错误，不修改源文件和默认保护属性。

部件编号必须保持语义稳定。目录升级不能让相同编号生成不同图像；需要改变含义时增加新版本并保留旧版本解码或提供显式迁移。固件通过 capability 和目录标识/版本告知 App 是否支持 ID-only。

## 保存确认、重复请求与冲突

建议状态为“编辑中 → 正在保存 → 正在核对 → 已保存”，另有明确的“结果待确认”和“冲突”。

1. 新增前生成固定 UUID ID，并在首次发送前将目标 ID、目标板 ID、提交快照及待确认状态落盘到草稿存储。App 退出后恢复同一操作，不能重新生成 ID。现有固件已经接受客户端给出的新 ID，无需先扩展协议才能避免无 ID 重试生成另一项。
2. 将板 ID、连接代次、草稿快照、目标 ID 固定到本次操作。关闭命名不向板子写入。
3. 更新时使用开始编辑时的 expect{name,frameHex} 和 bootId/gen。只有本会话明确成功完成的同 ID 重命名，且确认其版本与内容时，才可显式推进编辑基线；reload 学到的他端名字或最新 gen 不得自动替换旧编辑基线。
4. 固件先校验并准备完整的候选运行内容，再完整写临时文件、替换正式文件、发布已经准备好的运行内容，最后回成功。候选准备失败时不替换文件。文件成功替换后仍发生安装问题时，回复须明确表达“已落盘但运行列表未就绪”，不能把它当成“没有保存”而诱使客户端再新增。实施时优先让最终发布阶段不再需要失败风险较高的分配。
5. App 收到成功后 GET_FACES 读回，核对同 ID 的类型、名称、内容/部件编号及顺序。通过后更新正式列表和编辑目标。
6. ACK 或读回丢失时保留已知目标 ID，显示“结果待确认”。先读同一板核对：内容完全相符则已保存；不存在才允许以同一 ID 重试，并以新增协议的 createOnly 和版本条件在固件提交点原子检查“仍不存在”；已有不同内容则提示冲突。不自动生成第二个 ID，不做无界重试。固定 UUID 只能避免重复 ID，不能单独提供完整幂等性；不承诺每次重试的计数器/闪存副作用仅执行一次。

已存在的 upsert 期望检查不等于整库事务版本检查。初版改动包含写操作的版本条件：新增可选 expectedBootId/expectedGen 和 createOnly（用于创建），在同一 Core-0 提交路径上先检查再修改；重命名、删除、重排、覆盖和整库导入均应用版本条件，整库上传在结束提交点再次检查。新客户端在能力确认后使用这些条件。旧客户端沿用原协议，不能宣称旧客户端的无条件写操作获得全部并发保证；当前固件的串行增量更新也不能被误报为两个新增请求会并行覆盖同一个旧文件。

App 的版本游标以物理板 ID、bootId 和 gen 共同限定。gen 当前是启动期内存计数，重启后必须重新读取；不需要为此频繁把 gen 写入闪存。

## 读取与缓存

App 只持有当前连接的内存快照。GET_FACES 按现有 gen 分页规则读取，出现 409 按现有边界重新读取；完整解析和校验成功后一次性发布，避免半份列表。

具体兼容决定：磁盘可以只存 parts 引用，GET_FACES 默认返回扩展后的视图，所有项都有旧客户端可读的 frameBytes，parts 另附 call、partsCatalog、partsVersion。新 App 同样使用这个表示读取列表和缩略图，初版不增加 canonical-only 读取模式。只有保存 ID-only 的写入能力需要协商，避免旧 App 宽松解码器把新保存项静默丢弃。

现有 GET_FACES 直接读取磁盘字节，实施时必须改为固定代次的不可变扩展快照：所有分页长度、offset 和 gen 都针对同一份投影字节。目录变化或 bootId 变化后旧分页失效，返回冲突并重新读取。快照可按连接有界分配或按代次共享；实现计划需量化最大 128 项、最多两条 TCP 加 BLE 下的峰值 PSRAM与生命周期，不能每个分页重新从可变文档生成不同字节。

切板立即撤下旧列表并取消其 UI 发布资格。旧操作的晚到回复可以说明原板上的真实结果，但不得覆盖新板列表。断线后隐藏列表；重连后重新读取，即使是同一块板，也不把上次内存内容当成已确认的最新数据。

没有云端同步、离线正式表情库或后台自动把本机数据传给任意新板子的行为。显式导出文件仍可以作为用户选择的备份，不作为 App 日常表情库。

## 旧数据和兼容

- 现有 default/custom/parts+frameBytes 文档继续可读，不改现有默认表情 ID、顺序、启动标记和保护规则。
- 旧 parts 只有在对应目录下重组结果与原位图逐字节一致时，才能无损转换成只存编号；不一致则保留位图。
- 新 App 连旧固件时仍可保存完整位图，新固件确认能力后才发送 ID-only。
- 旧客户端得到完整位图投影，整库上传后仍可按旧位图格式保存；只有版本/编号可确认且重组位图完全一致时才转换为引用。不要求旧客户端理解 canonical 引用文件。旧客户端不会因 GET_FACES 缺失 frameBytes 而丢项，但其无条件整库写入的冲突保证仍受上一节的兼容范围限制。
- 已有 local_faces.json 保留原始内容；通过显式的一次性迁移入口把选中的旧本机表情复制到用户指定的板子并逐项核对。迁移固定源文件快照和目标板 ID，为每个源项使用可重复计算的稳定目标 ID，避免中断后再次新增。取消或失败保留旧数据，不自动删除，也不在离线保存列表中继续展示旧本机库。草稿存储继续用于用户已允许的未提交内容恢复。

## 改动范围草案

| 部分 | 预计涉及 |
|---|---|
| 固件部件表 | 同源生成工具、生成的只读部件表、部件合成模块 |
| 固件保存 | storage.cpp、protocol.cpp、state.h 按需扩展、能力与协议文档 |
| App 保存模型 | FaceDocument、FaceUpsertPayload、BoardConnection、FaceLibraryModel |
| App 编辑与界面 | ControlView/ControlViewModel、FaceLibraryView、RootTabView 的切板与断线处理 |
| 本机旧库和草稿 | LocalFaceStore 的旧库迁移入口及停止正式表情新写入；DraftStorage 保留未提交恢复语义 |
| 验证 | 保存/冲突/切板回归、部件跨端一致性、固件主机故障注入、两板串口验收 |

这是跨固件与 App 的功能改动，实施前需要按最终认可范围展开具体文件清单与实现计划。本轮未修改这些产品实现，也未提交、推送或烧录新固件。

## 后续实施的验收标准

- 离线入口与已打开列表均遵守隐藏规则；不会退回本机库。
- 两种格式新增、覆盖、另存、重命名、删除、排序、重连、切板及重启后读回正确。
- 客户端已知新 ID 的丢 ACK/丢读回场景不产生重复项，结果不明不会显示已核对成功。
- 新版条件写客户端之间，外部重命名、画面修改、并发整库导入不会被静默覆盖；旧客户端无条件写入的限制与正文兼容范围一致。
- 全部单部件与代表组合的 App/固件结果一致，包括空部件、别名、镜像和尾部无效位。
- 纯部件仅保存编号；改一个像素后必须改存位图；旧位图读回和默认表情保护不变。
- 未知部件/版本和空间不足均不破坏原文件，坏输入不能进入运行切换列表。
- 两板串口 btn B1/B2 遍历每项并回读，B3 自动模式遍历全部已保存项；App 断开后继续运行；重启后列表保留。
- 保存、读取和重启测试完成后，临时表情清理，原有表情与显示设置恢复。

本轮测试结果和原始证据另见 /tmp/rina-save-review。真实断电瞬间写入的测试不等同于正常重启，需要独立硬件条件；本轮以已有主机故障注入验证写失败保护。
