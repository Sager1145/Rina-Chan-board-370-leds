# 多板保存内容不同时的控制逻辑

状态：设计建议。本轮用户已明确默认“以主板为准，两板显示同一张”；其余边界是下面提出的实现规则，尚未新增群控功能代码。

## 基本规则

每板的正式表情库仍独立。群控同步的是当前画面，不是保存库。

- 群控上一张、下一张和自动轮播只采用主板的表情列表及顺序。从板自己的数量、顺序、名称和 ID 不影响结果。
- 主板成功选定后，取得最终的 47 字节逻辑像素帧，再把同一帧临时显示到从板。不要向从板重放主板的索引或表情 ID。
- 跟随显示不写 flash、不新增表情、不移动从板的本地保存列表游标。退出群控后从板仍保留自己的内容。
- 亮度、颜色和轮播间隔属于群控设置，可以统一下发；失败逐板显示，不能以主板成功冒充全部成功。

例：主板保存“开心、眨眼、生气”，从板只保存“爱心”。群控下一张选到主板“眨眼”，从板临时显示同样像素；它的保存库仍只有“爱心”。

当前群控上一张、下一张和自动轮播由 GroupAutoCycler 取主板列表中的位图，通过 setFrame 向成员发送；指定保存表情和 App 按钮命令的 resolveFace 路径才会在主板成功回复后解析画面再转发。现有直接位图转发发生在主板 ACK 之前，因此“所有群控表情都先确认主板成功再转发”仍是本方案待补的约束，不能宣称已经实现。新保存架构不应把这些动作改成跨板 ID/序号调用。

## 身份与界面

保存项的身份是“板子物理身份 + 板内表情 ID”。相同 ID、名称或序号不能说明两个板上是同一内容；像素摘要可以核对画面，但不能代替保存项身份或擅自合并用户保存项。

群控保存列表明确标“主板表情 · 板名”，从板状态显示“跟随主板”。如需要查看从板自己的保存列表，应显式切到该单板目标。不要将多板列表混合成没有来源的一张列表。

“保存”默认保存到标明名称的主板。另设显式“保存到所选板”才允许多板保存：每个目标有独立的固定操作 ID、版本检查、读回确认和结果。部分成功如实显示，不自动删掉成功项来伪装原子事务，不自动复制整库。

## 重连、主板离线和失败

- 每次群控会话/主板切换有新的控制代次，每次画面有递增序号。断线丢弃该成员尚未发送的旧命令和帧。
- 从板重连，确认物理身份和新连接代次后，只对齐仍然有效的群控会话的最新完整画面；不回放错过的切换步骤，不先显示旧队列。
- 主板暂时离线时建议保持最后画面并暂停群控轮播。通讯控制通道可以重建，但表情来源不能悄悄换成另一个板的库。
- 用户明确换主板后，重新读取新主板的列表和当前游标，建立新控制代次，不继承旧主板的序号。此规则比现有自动主板提升更严格，需要单独调整并验证后才能宣称已实现。
- 从板失败不阻塞其他已连接板操作；显示“部分连接/部分成功”，重连后只追最新画面。

普通表情每次转发的像素内容为 47 字节，另有命令元数据和协议开销；先统一使用完整位图，避免从板部件版本不同导致画面分歧。切换和跟随不传整库；列表载入、保存核对、重连、迁移和导入仍可能读取或传输表情库，版本未变时可条件确认后复用内存快照。不能将各 BLE 链路的成功理解为毫秒级同时显示。

首次进入群控时，也要读取并对齐主板的当前完整画面，固定其物理身份、启动与表情库版本后才开始轮播，不能等用户再点一次。现有首次加入可能尚无 lastDispatchedFrame，这条即时对齐同样属于待补行为。

## 实体按键与脱离 App

下述实体接管规则为设计建议，尚未新增检测逻辑。单板的按钮和板端自动轮播继续使用该板自己的保存库。首版群控以 App 的群控操作为统一入口，不默默把任意从板实体按键当成全组命令。

如后续要让主板实体按钮也驱动全组，建议增加带 bootId/递增事件号的明确 GPIO 动作事件；App 只接受当前主板事件，解析主板实际画面后再转发，避免依靠名字、序号或状态变化猜测并形成回声循环。从板实体操作应视为本地接管并提示偏离跟随，重新加入需明确动作。

App 不连接时，各板只能保证自己的保存、按钮和独立自动轮播。若要求无 App 时多板持续联动，需要另行设计板间通信，不应靠保存库恰好一致假装已经支持。

## 后续验收

- 首次进入群控立即对齐当前画面，主板未成功接收时不误报整组成功。
- 两板不同数量/顺序/同名异图/同 ID 异图，群控后显示主板画面，从板保存库逐项不变。
- 同一帧在不同部件版本的板子上结果一致。
- 快速连续切换、从板掉线重连不会回放旧帧；主板离线不会隐式换库。
- 多板保存部分失败后重试不重复新增，也不覆盖他端编辑。
- 退出群控、实体本地接管与重新加入的规则明确可观察。
