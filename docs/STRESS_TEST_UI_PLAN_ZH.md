# RinaBoard App 发令功能压力测试计划（UI 驱动）

编写于 2026-09-13，依据当前工作区（HEAD `1e81ff0` + 未提交修改）的 iOS 与固件源码。本计划补充 `STRESS_TEST_PROMPT_ZH.md`：那份测协议层与主机侧；本计划从 **App 界面** 出发，要求点遍每个会向板子发指令的控件，覆盖所有输出来源之间的切换及功能组合，并做大量快速切换。执行前应重新核对源码；源码与本文不一致时以源码为准，并在报告里写明差异。

---

## 0. 目标与判定原则

1. **覆盖**：`RinaCommand.swift` 中每个 CMD、`RinaLinkMessageType.swift` 中每个请求帧类型，都至少有一次由 App 界面真实触发，且在板端串口日志中留有记录。确实没有 UI 入口的，通过 调试 → 串口监视器 / 原始命令控制台 触发，并在覆盖表中标为「仅调试入口」。
2. **切换**：7 个输出来源（`BoardOutputSource`：manual、automatic、text、lipSync、performance、video、debug）两两之间的 42 个有向切换，加上 7 个同来源重启，全部执行。
3. **组合**：全局设置（颜色、亮度、自动/手动、自动间隔）× 每个输出来源；每个页面内会影响输出的参数两两组合。
4. **大量切换**：固定随机种子的长序列连打、滑块拖拽风暴、标签页轮转、前后台与断连循环。
5. **多板**：≥ 2 块板之间，经每个切换入口反复切换；覆盖切换前后正在进行的发令、播放和事务，以及多块板同时在线的情况。
6. **硬性不变量**（任一违反即 FAIL）：
   - App 不崩溃（PID 不变）、不卡死（主线程停顿 < 1 s），板子无重启或 watchdog。
   - 新来源接管后，旧来源不再发送帧。检查方法：串口日志中接管时刻之后，不再出现旧来源 reason 前缀（`lipsync:` / `live_preset:` / `video:` / `debug_*` / `custom_*`）的帧。
   - 负载停止后等 3 s（超过 2 s 回显抑制窗口），UI 显示值与 `GET_STATUS` 一致，包括颜色、亮度、模式、自动间隔、表情序号、`outputMode`、`outputStreamID`；UI 预览与 `GET_FRAME` 一致。
   - 同一连续操作序列中，最后一次操作的结果必须是最终状态（latest-wins）；中间值被丢弃允许，但须记录。
   - 失败操作不破坏已有数据：表情库哈希不变，文字时间线不会残留 `active=1, frameCount=0`。
   - 调节亮度、颜色、循环开关、文字 FPS **不得抢占**输出所有权。
   - **命令不串板**：每块板串口日志里的每条命令，都能对应到该板为当前控制对象时执行的某个 UI 步骤。串板一次即 FAIL。

| 多板硬件 | 至少 2 块板（A、B），最好 3 块（C 用于离线和三方切换）。每块板的快照、表情库备份和 flash 预算都单独记录。 |
| 多板可辨识状态 | 测试前让各板状态明显不同，串板时一眼就能看出来。例如 A：红色、亮度 25、手动、表情 1；B：蓝色、亮度 80、自动、间隔 2 s。颜色等设置结束后恢复。 |
| 多板观测 | 每块板一个 USB 串口，同一主机时钟打时间戳，合并成一份按时间排序的日志。UI 步骤 CSV 增加「当前控制对象」列。 |

### 驱动方式（按优先级）

1. **XCUITest 真机**（首选）：复用 `ios/RinaBoardUITests`，为缺少 accessibilityIdentifier 的控件补标识（只改标识，不改行为）。随机序列统一用固定种子；每步记录「主机时间戳、步骤 ID、控件、参数」到 CSV，便于和串口日志对齐。
2. **Device Hub + 电脑操控**（后备）：页面滚动后坐标会漂移，每次点击前先 zoom 确认。上次有一次误点把进度条拖到了 221 帧。
3. **人工**：仅用于麦克风、音频中断、锁屏、来电等自动化难以覆盖的步骤。

## 7. 多板连接切换（MB 类）

### 7.1 先从代码核实的行为（2026-09-13 读码结论，执行前复核）

- **支持多块板同时在线**：`BoardSessionStore` 为每块板维护一个 `BoardSession`，各自持有一个 `BoardConnection`；同一时刻只有一个是 active，UI 就连到它（`BoardSessionStore.swift:50-129`，`RinaBoardApp.swift:27-42`）。
- **两个切换入口的机制不同**，两者都要测：
  - **E1 连接页「控制对象」行**：调用 `sessions.select`，只切换 active 会话，旧板**保持连接**，旧会话的输出租约被 invalidate（`BoardSessionStore.swift:90-94`）。
  - **E2 控制中心「面板」菜单**：复用**当前**这个 `BoardConnection`，先断开旧板再连新板（`BoardControlCenterView.swift:159-167` → `connectSavedBoard` → `connect(using:)`）。
- **其他入口**：
  - E3：连接页的已保存面板行、扫描列表点击。
  - E4：启动时自动重连，选 `lastSeen` 最新的板；如果用户已手动选了板，以手动为准（`RootTabView.swift:367-384`）。
  - E5：忘记面板。
- **切换中与失败时的行为**：
  - 切换进行中，E2 菜单禁用；E3 再点会被静默忽略，不会排队。
  - 目标板离线时**不会回退**到旧板：重连同一目标 5 次（退避最长 30 s），之后进入 failed。
  - App 里没有 BLE ⇄ Wi-Fi 自动回落。
- **状态隔离依赖 `connectionGeneration` 守卫，不是按板分实例**：编辑器、文字、控制中心、表情库、口型、演出、视频的模型都是 App 级单例（`RinaBoardApp.swift:12-18`），换板时由 `RootTabView.swift:115-130` 统一重置并重新同步：
  - 控制中心：取消亮度、颜色、间隔三个 LatestValueSender 中待发的值，清空回显抑制窗口（`BoardControlCenterModel.swift:122-136`）。
  - 表情库：旧代次发起的写操作被 `validateBoard` 拦截，提示「面板已更换」（`FaceLibraryModel.swift:721-732`）。
  - 文字：`restoreOnConnect` 多处复核代次，丢弃旧板的 `GET_SCROLL_META` 结果。
  - 口型：换板后停止。
  - 演出、视频：只停止向板子发帧，**手机本地的播放和声音继续**；需要手动「继续输出到面板」才会发往新板（演出页没有这个按钮）。
  - 编辑器草稿：当前代码**跨板保留**，`connectionChanged` 只清 `sentGeneration`，不清草稿。**已定预期（2026-09-13）：换板时直接放弃未保存的画面**，因此当前代码下 MB-05 预期 FAIL，需改代码后回归。
- **待验证疑点**：E2 路径复用同一个连接对象，而 `disconnect()` / `connect()` 里没找到清空 `framePump` / `commandPump` 排队任务的代码。给 A 排队但还没开始的帧或命令，可能在连上 B 之后发出去。MB-03 专门验证这一点。
- **固件侧**：每块板的 mDNS 主机名、Bonjour 实例名、默认 AP SSID 都带 MAC 后缀（`board_identity.cpp:8-34`），同一局域网里理论上不冲突；每块板最多 2 个 TCP 客户端（`transport_tcp.cpp:17`）。
- **现有测试**只有 `ConnectionLifecycleTests` 中的 2 个切换用例和 `BoardConnectionOutputTests.testConfiguredNameFollowsBoardSwitchAndDisconnect`；E1 多会话路径和 E2 热切换路径都没有专门测试。

| MB-05 | 未保存画面换板即放弃 | 在 A 上画一个未存入表情库的画面，分别通过 E1、E2、E3 切到 B 后：<br>① 实时预览关，点「发送」<br>② 实时预览开，点一个 LED<br>③ 点「撤销」<br>④ 切回 A<br>⑤ 杀 App 重启<br>另测：在 A 上编辑表情库里已有的表情但未保存，再切到 B | 换板后编辑器不再显示 A 的画面，**不弹确认、直接放弃**。<br>①② 发往 B 的帧只基于 B 的画面，日志里不出现 A 草稿的帧。<br>③ 撤销不能恢复 A 的草稿。<br>④⑤ A 的草稿不会回来，本地保存的草稿也已清除。<br>另测：A 表情库里的原表情不变，编辑状态被清除，「保存」不会写到 B 的库 |

| MB-07 | 双板各自滚文字 | A 滚文本 1、B 滚文本 2，用 E1 来回切 20 次；在 B 上暂停、seek、改 fps、切循环 | App 显示的文本、进度、fps、循环始终跟随当前板；在 B 上的操作不影响 A |
| MB-08 | 切换中再操作 | 在 connecting 期间：点另一块板、点同一块板、点断开、切标签页、拉起控制中心 | 最终只连到最后一个有效目标；不出现两个会话指向同一块板；按钮禁用状态正确；无悬挂的「连接中」 |
| MB-09 | 目标离线或掉电 | B 断电或远离后切到 B；切换握手进行中给 B 断电；B 进入 failed 后切回 A | 有明确错误提示，不假装已连接；控件禁用；5 次退避后进入 failed；切回 A 正常，A 不受影响 |
| MB-10 | 同一块板被重复连接 | B 已在另一个会话里连着，再从 E2 菜单或扫描列表把当前会话连向 B | B 的日志中没有重复订阅或重复命令；App 只有一个会话对应 B；UI 不出现两个 B |
| MB-11 | 启动自动重连选板 | A、B 都连过，杀 App 重启 ×10：交替让 A、B 成为最后使用的板；启动后立刻手动选另一块；最后使用的板关机时重启 | 连 `lastSeen` 最新的板；手动选择优先；目标离线时行为明确，不卡在启动动画 |
| MB-12 | 忘记面板 | 忘记 active 板、忘记非 active 的在线板、忘记后重新扫描连接 | 被忘记的板断开且从列表消失；其余会话不受影响；重连后偏好的传输方式正确 |
| MB-13 | 混合传输 | A 走 BLE、B 走 Wi-Fi TCP 或热点直连，再做 MB-01、MB-03 | 条件不足时标 BLOCKED；加入热点期间 A 的 BLE 不断 |
| MB-14 | 同名板 | 把 A、B 改成相同设备名（已获同意，2026-09-13；计入改名预算，结束后恢复原名），再做 MB-01 | 列表能靠标识区分两块板；每次都连到正确的板；Bonjour 实例名不冲突 |
| MB-15 | 一板多手机（可选，需第二台手机） | 两台手机同时连 A（BLE + TCP）；第三个 TCP 连接应被拒；手机 1 播视频，手机 2 调颜色、抢占输出 | 所有权转移明确；两台手机的 UI 最终与板一致 |

## 9. 交付物

输出到 `docs/stress-ui-<实际时间戳>/`：

1. `REPORT.md`：被测版本、实际覆盖、发现（带严重度、最小复现和 `file:line`）、未测项及原因、测试副作用与恢复情况。
2. `COVERAGE.csv`：第 2.10 节每一行 → 触发的用例 ID、首次命中的日志行号、状态（HIT / 仅调试入口 / BLOCKED）。
3. `CASES.csv`：`case_id, 类别, 入口, 控件, 参数, 前置来源, 次数, 种子, 结果 PASS/FAIL/BLOCKED/NOT_RUN, 证据路径`。
4. `SWITCH_MATRIX.csv`：7×7 矩阵，每格填通过次数/总次数和失败证据。
5. `MULTIBOARD.csv`：`step, 种子, 入口, 源板, 目标板, 切换前动作, 距切换 ms, A 预期命令, A 实际命令, B 预期命令, B 实际命令, 串板, 结果`；另附每块板的串口日志和合并日志。
6. `logs/`：串口原始日志、UI 操作步骤 CSV（主机时间戳）、App 调试日志导出、崩溃报告。
7. `metrics/`：heap、`refreshMaxUs`、App RSS 曲线；各滑块风暴的发送速率统计。
8. `RUNBOOK.md`：构建与安装命令、驱动脚本、种子、设备身份、恢复步骤。

注意：不同轮次的重复运行不能相加充当覆盖数；历史报告里的 PASS/FAIL 只作回归参考，必须在当前版本上重新跑。
